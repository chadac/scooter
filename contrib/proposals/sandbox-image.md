# Proposal: a contrib extends the sandbox image

**Status:** proposal, for review. No code. See #595 for why contrib is the
home for optional user-facing features, and #594 / #593 for the two features
that need surfaces contrib does not have yet.

A contrib can plug into the broker and the webhooks service. **aws grants**
needs a third target: the sandbox image. This proposes the option schema and
names the constraints that decide its shape.

## Why aws forces this

The feature is one thing to a user — *request access, a human approves in the
conversation, `aws --profile … ` works* — and four things in the tree:

| half | where it lives today |
|---|---|
| routes + grant/approval logic | `services/broker/broker/aws/` (~1868 lines) |
| state | the `permission_requests` table |
| the in-sandbox CLI | `pkgs/broker-tools/` — builds `scooter-aws` by **embedding the broker's own `aws/cli.py`** |
| the agent's instructions | `skills/scooter-aws.md` (140 lines, in the app's flat skills dir) |

Plus `modules/sandbox-os/carry-over.nix`, which renders `~/.aws/config` from the
accounts ConfigMap during activation.

The third row is the interesting one. `pkgs/broker-tools/default.nix` says it
*"embed[s] the broker service's own cli.py so the in-sandbox helper can't
drift from the broker"* — a cross-tree reach that exists precisely because one
feature's two halves live in two trees. Making aws a contrib is what lets that
coupling become local instead of cross-tree; without a sandbox surface,
migrating aws would make it *worse*, with the contrib on one side and
`pkgs/broker-tools` still reaching for a file that moved.

## Proposed schema

A sibling to `services`, in `contrib/submodule.nix`:

```nix
contribs.aws = {
  sandbox = {
    enable = true;

    # Prebuilt into the image. For tools that must always be present.
    packages = ps: [ ps.scooterContrib.aws.cli ];

    # …or shipped as a nix-stubs shim: the image carries the recipe, the tool
    # arrives on first use. See "laziness" below — this needs stubs.lock.
    lazyPackages = ps: [ ps.awscli2 ];

    # A NixOS module merged into the sandbox-os config at image build: systemd
    # units, activation scripts (the ~/.aws/config render), env.
    module = ./sandbox.nix;

    # Markdown merged into the agent-skills set (see "skills" below).
    skills = ./skills;
  };
};
```

`enable = false` means absent from the image — no package, no unit, no skill —
matching the existing top-level `enable` semantics (*"`false` means absent — no
derivation at all"*).

## Mechanism

The sandbox image is built with `pkgs.nixos` (flake.nix), so contrib-contributed
NixOS modules are appended to its module list at image build. That is ordinary
Nix module composition — the same thing #585 already does for contribs
themselves — not a new discovery mechanism.

Note what this is **not**: it is build-time and deployment-wide. The image is
shared by every conversation, so a contrib's sandbox contribution cannot vary
per conversation. The per-conversation path (`webServices`, `mcpServers`,
`/etc/scooter/modules/`) is a separate mechanism handled separately; this
proposal deliberately does not touch it.

## Three constraints that shape it

**1. The in-pod re-converge vendors `modules/sandbox-os/`.** `stubs.nix` says it
lives there *"so the in-pod re-converge (which vendors this tree) evaluates the
same declarations instead of rebuilding the tools at full size"*. A contrib
sandbox module living under `contrib/<name>/` is therefore **outside** what the
converge vendors, and an in-pod rebuild would evaluate a different module set
than the image was built from. This is the load-bearing question of the
proposal: either the converge vendors contrib sandbox modules too, or a
contrib's sandbox module is materialised into the vendored tree at image build.
Getting this wrong produces a sandbox that silently differs after a rebuild.

**2. Laziness needs the lock.** Every enabled contrib's `packages` land in every
sandbox, so image size is a shared cost. `stubs.nix` is the existing answer, but
its `stubs.lock` is generated by `nix run .#stubs-gen` and keyed by system +
attr — so `lazyPackages` requires `stubs-gen` to walk the contrib set, and a new
contrib tool means a lock regeneration. That is a real papercut against
"adding a contrib is a new directory", and it argues for `packages` (baked) as
the default and `lazyPackages` as opt-in for anything large.

**3. Coupling to the service halves.** `scooter-aws` is useless without the
broker half serving its endpoints. The schema should assert that — a contrib
declaring `sandbox.enable` with its broker half disabled is an eval error, the
same spirit as the existing fixed key set where *"a typo is an eval error"*.

## Skills are a fifth surface, and nearly free

`skills/` is a flat directory read by `flake.nix` into an attrset and rendered
to the `agent-skills` ConfigMap. Several entries are per-feature, not
per-platform:

| skill | belongs to |
|---|---|
| `scooter-aws.md` | aws |
| `scooter-publish.md` | shares (#594) |
| `scooter-datadog.md` | datadog (already a contrib) |
| `scooter-github.md` | github (#591) |
| `slack-formatting.md` | slack (#588) |

So `datadog` is already a contrib whose *documentation* still lives in the app.
Merging `contribs.<name>.sandbox.skills` into the skills attrset needs no
codegen — it is an attrset union plus a name-collision assertion — and it is
worth doing first, independently of the rest of this proposal, because it
removes a per-feature app edit for every contrib that already exists.

## Open questions

- Does the converge vendor contrib modules, or do contrib modules get
  materialised into the vendored tree? (Constraint 1 — needs a decision before
  any code.)
- Should `sandbox.packages` be able to shadow an app tool, or is that an error?
- Does the accounts-ConfigMap render in `carry-over.nix` move into the aws
  contrib's module, or stay platform-side because the ConfigMap is a deployment
  concern?
