# `lib/sql` — the declarative shared-database schema (Atlas-owned)

This directory holds the **DDL** for every Postgres table Scooter's services share.
The per-language ORM bindings (`@scooter/schema` for TypeScript, `scooter_schema` for
Python) are **generated** from these schemas — you never hand-write them. See
`todo/draft/DECLARATIVE_SCHEMA_ATLAS.md` for the design.

## Two sources, and which is which

The **topology** — which databases exist, which tables are in each, who writes and who
reads — lives in the **module system**, as `agentSandbox.db.<database>` (see
`modules/db-spec.nix`, issue #606). The **DDL** — columns, indexes, constraints — lives
here. Nix owns only the facts that have to agree across the deployment; SQL stays SQL.

Two files in this directory are therefore **generated** from that option and must not
be hand-edited (CI fails on drift via `just db-generate-check`):

```
lib/sql/
  owners.toml               # @generated — who writes/reads each table
  atlas.hcl                 # @generated — one Atlas env per database
  <db>/schema.sql           # declarative END-STATE DDL for that database — edit HERE
  <db>/migrations/          # generated by `just db-migrate`; reviewed, never hand-authored
```

To add a **table**: declare it in the owning module's `agentSandbox.db.<database>.tables`,
write its DDL into `<db>/schema.sql`, then `just db-generate && just db-migrate <name>`.
The ownership manifest, the migrator's database list and the postgres GRANTs all follow
from the declaration — there is no second list to update.

`owners.toml` is the readable rendering of the topology: read it to answer "who may
write `resource_links`?". `schema.sql` is **declarative end-state DDL**: read it to answer "what columns does
`conversation_map` have?" without replaying migration history. Column types mirror
what production already has — tables historically defined via SQLAlchemy `String`
are `character varying`; the agent-host raw-DDL stores are `text`. A type change
here is a real migration; do not "tidy" them apart.

## Workflow

Everything runs against an **ephemeral, per-invocation local Postgres** (Atlas's
"dev database"), spun up and torn down by `scripts/atlas-dev.sh`. Nothing touches a
shared or production server, so concurrent runs never interfere.

```bash
# 1. For a NEW table: declare its ownership in the module that owns the service.
$EDITOR modules/webhooks.nix        # agentSandbox.db.webhooks.tables.<name>

# 2. Edit the end-state DDL you want:
$EDITOR lib/sql/webhooks/schema.sql

# 3. Generate the migration(s). Only databases that actually changed get a file.
just db-migrate add_slack_ts_index

# 4. Regenerate the spec artifacts + ORM bindings, and confirm no drift:
just db-generate      # owners.toml + atlas.hcl + @scooter/schema / scooter_schema

# 5. Review the new migration + regenerated output, commit.
```

`just db-validate` checks every migration directory (ordering, checksums,
replayability).

## Deploy

Migrations are applied on deploy by the migration Job (`modules/db-migrate.nix`),
which runs `atlas migrate apply --baseline <baseline>` per database against the
shared server. `--baseline` adopts the current production tables on first run
(they already exist, created by the services) without re-executing the baseline,
then applies any later migrations. The same command is safe to run every deploy.

## Rules

- **Never** hand-edit files under `<db>/migrations/` or the generated ORM packages.
- **Never** add a table via a service's inline `CREATE TABLE` / `create_all` — add
  it to the owning database's `schema.sql` and regenerate.
- The `openfga` database is owned by the OpenFGA migrator, not Atlas — intentionally
  not modelled here.
