# `lib/sql` — the declarative shared-database schema (Atlas-owned)

This directory is the **single source of truth** for every Postgres table Scooter's
services share. The per-language ORM bindings (`@scooter/schema` for TypeScript,
`scooter_schema` for Python) are **generated** from these schemas — you never
hand-write them. See `todo/draft/DECLARATIVE_SCHEMA_ATLAS.md` for the design.

## Layout

Tables are partitioned across **per-service databases** on the one shared Postgres
server, so there is one Atlas env per database:

```
lib/sql/
  atlas.hcl                 # one env per database (webhooks, scheduler, broker, byoc)
  <db>/schema.sql           # declarative END-STATE for that database — edit HERE
  <db>/migrations/          # generated by `just db-migrate`; reviewed, never hand-authored
```

| Database | Owner service | Tables |
|----------|---------------|--------|
| `webhooks` | webhooks (+ agent-host writes `user_identity`, `remote_agents`; reads `conversation_map`) | conversation_map, jira_tickets, resource_links, pending_messages, credential_scopes, user_identity, remote_agents |
| `scheduler` | scheduler | scheduled_tasks, task_runs |
| `broker` | broker | sandbox_size, permission_requests |
| `byoc` | byoc-controller | remote_agents *(with `session_id` — a distinct table from the webhooks-db copy)* |

`schema.sql` is **declarative end-state DDL**: read it to answer "what columns does
`conversation_map` have?" without replaying migration history. Column types mirror
what production already has — tables historically defined via SQLAlchemy `String`
are `character varying`; the agent-host raw-DDL stores are `text`. A type change
here is a real migration; do not "tidy" them apart.

## Workflow

Everything runs against an **ephemeral, per-invocation local Postgres** (Atlas's
"dev database"), spun up and torn down by `scripts/atlas-dev.sh`. Nothing touches a
shared or production server, so concurrent runs never interfere.

```bash
# 1. Edit the end-state you want:
$EDITOR lib/sql/webhooks/schema.sql

# 2. Generate the migration(s). Only databases that actually changed get a file.
just db-migrate add_slack_ts_index

# 3. Regenerate the ORM bindings + confirm no drift (added in the generation PR):
just db-generate      # (see @scooter/schema / scooter_schema)

# 4. Review the new migration + regenerated bindings, commit.
```

`just db-validate` checks every migration directory (ordering, checksums,
replayability).

## Deploy

Migrations are applied on deploy by the migration Job (`modules/db-migrate.nix`),
which runs `atlas migrate apply --baseline <baseline>` per database against the
shared server. `--baseline` adopts the current production tables on first run
(they already exist, created by the services) without re-executing the baseline,
then applies any later migrations. The same command is safe to run every deploy.

## Rules

- **Never** hand-edit files under `<db>/migrations/` or the generated ORM packages.
- **Never** add a table via a service's inline `CREATE TABLE` / `create_all` — add
  it to the owning database's `schema.sql` and regenerate.
- The `openfga` database is owned by the OpenFGA migrator, not Atlas — intentionally
  not modelled here.
